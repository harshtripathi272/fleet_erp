# Notes for AI assistants

Everything about this project is in [README.md](README.md): what the app does, the context behind decisions, setup, the console, how the API behaves, and the code layout. The work list is [issue #140](https://github.com/harshtripathi272/fleet_erp/issues/140); questions for Lakshya go on [#23](https://github.com/harshtripathi272/fleet_erp/issues/23), elaborated, never one-liners.

The founding principle, at the top of the README: one company = one copy of this repository = one deploy. `main` holds the fundamentals (trips, consignments, rate contracts, settlements, profit); a company's own features go in its fork, with no global updates. The codebase is a configurable base for many transport companies that each work differently. Everything a company might do differently is configuration with sensible defaults, never a value fixed in code; a client's rules are that client's settings; setting up a new company should be easy without changing the core.

The README separates what is settled (the founding principle, the stack, how we work) from what is open (model grouping, screen layouts, UI guidance, code suggestions). Treat the open parts as current thinking, not a specification. When a task is not covered, or something looks wrong for the task, ask rather than assume. If a task seems to need a library, service or pattern outside the agreed stack, propose it first.

Before starting work, read [AGENTS.md](AGENTS.md) and run `scripts/inbox.sh <your-name>`. You work in your own git worktree on your own branch, open a pull request into `develop`, and the coordinator (lakshya-t3) reviews and merges it. Build features from real transporter scenarios, written as tests first, not tests written to fit features. Simulated services stay, labelled "simulated"; a switch that does nothing isn't shown.
